# Синтетический генератор датасета заявок к врачу

Генерирует пары «текст пользователя → semantic frame из label-токенов» для
обучения маленького decoder-only Transformer с нуля (гибридная схема:
закрытый словарь → токен, открытая поверхность → хардкод-парсер).

Каталог интентов — телефонный регистратурный контур (регламент РГ-ТЕЛ-01):
13 интентов (book/reschedule/cancel/check_booking/home_visit/schedule/
lab_status/paid/waitlist/docs/complaint/medical/unsupported) плюс
тривиальные пути `<YES>`/`<NO>` — голые «да»/«нет» как самостоятельные
реплики-подтверждения. Менеджер диалога телефонии на этой схеме —
`telephone/` (см. его README).

## Запуск

```bash
python synth/build_dataset.py                # train 20k (добирает ~14k), остальные по 1k
python synth/build_dataset.py --train 50000 --seed 42
```

Выход в `data/`: `train.jsonl`, `val.jsonl`, `test_iid.jsonl`, `test_ood.jsonl`,
`manual_gold.jsonl`, `stats.json`. Зависимостей нет — только stdlib.
Датасеты в репозиторий не коммитятся — полностью пересоздаются скриптами
`synth/`.

## Схема целевой последовательности

```
<INTENT> <SPECIALTY>
<TIME> [T_SCOPE] [T_DAY] [T_TIME] </TIME>   |   <T_UNKNOWN>
<SYMPTOM_*>... [<NEEDS_CLARIFICATION>] <END_FRAME>
```

Примеры:

```json
{"text": "запишите меня к зубному в следующую пятницу вечером, зуб ноет",
 "target": "<BOOK> <DENTIST> <TIME> T_NEXT_WEEK T_FRI T_EVENING </TIME> <SYMPTOM_TOOTHACHE> <END_FRAME>"}

{"text": "можно к терапевту, зуб ноет",
 "target": "<BOOK> <GP> <T_UNKNOWN> <SYMPTOM_TOOTHACHE> <END_FRAME>"}
```

Правило слота времени: T_SOON покрывает всё «ближайшее время» (T_ASAP слит по решению ревью: у бэкенда одно действие). Максимум один токен из каждой категории, порядок
`ОБЛАСТЬ -> ДЕНЬ -> ВРЕМЯ` (~60 фактор-токенов: `T_NEXT_WEEK`, `T_FRI`,
`T_H17_30`, `T_AFTER_WORK`, `T_MORNING`, ...; полный список —
`TEMPORAL_ENTRIES`/`TIME_*` в `synth/vocab.py`). `<T_AMBIG>` зарезервирован
для конфликтов («завтра или в пятницу»).

Таблица `TEMPORAL_ENTRIES` (сырая фраза → факторы) работает в обе стороны:
генератор сэмплирует факторы и рендерит фразу (метка точна по построению),
а хардкод-парсер приложения превращает сырую фразу в факторы для запроса
к бэкенду — таблица и есть парсер. Сырой спан (`frame.temporal`) остаётся
в каждой записи как якорь вербатим-валидации и материал для UI-подтверждения.

Ключевые проектные решения:

- **Закрытый словарь → токен, открытая поверхность → копия + хардкод.**
  Интенты/специальности/симптомы — классификация в закрытые списки
  (синонимы «стоматолог/зубной/дантист» → `<DENTIST>`); время — факторы
  по таблице, сырой спан сохраняется для валидации.
- **Нет опечаток.** Текст приходит из speech-to-text, поэтому шум только
  STT-характерный: регистр и пунктуация (3 варианта: как есть / всё нижним
  регистром / нижний регистр без знаков препинания).
- **Метка точна по построению.** Сначала сэмплируется фрейм (смысл), потом
  рилайзер превращает его в текст. LLM-контур, если добавится, тоже обязан
  генерировать только текст под известный фрейм и проходить round-trip
  валидатор.

## Архитектура генератора

| Файл | Роль |
| :-- | :-- |
| `synth/vocab.py` | Словари: специальности (формы nom/dat/ugen), симптомы, синонимы, скелетные фразы, временные chunks, пулы UNSUPPORTED |
| `synth/frames.py` | `Frame` + сэмплер осмысленных комбинаций, `target_string` |
| `synth/realize.py` | Скелеты предложений + STT-стилизация |
| `synth/validate.py` | Round-trip валидатор + `self_check()` пересечений «иголок» |
| `synth/split.py` | Дедупликация, сплиты без утечки |
| `synth/build_dataset.py` | CLI, статистика, ручной gold-набор |

Разнообразие возникает композиционно: ~20 скелетов × синонимы специальностей
(у каждой train- и ood-набор) × ~30 временных фраз × ~5 выражений на симптом
× опциональные приветствия/вежливость/порядок × 3 STT-стиля.

## Защита от утечки

- Тексты глобально уникальны (нормализованный дедуп на всё множество
  сплитов); фрейм может встретиться в нескольких сплитах с разными
  поверхностями — иначе тонкие интенты (check_booking, да/нет) не
  добирают объём ни в один сплит: их ключ-пространство мало, а блокировка
  «фрейм закреплён за первым сплитом» отдавала его целиком train.
  Исключение — тривиальные да/нет: атомарные реплики, повтор между
  сплитами не является утечкой парафраз.
- Сплиты заполняются последовательно (val → iid → ood → train), каждый
  получает план-распределение интентов.
- `test_ood` собирается из отдельного пространства поверхностей:
  - hold-out синонимы — после Этапа A ТЗ разговорные «окулист», «дантист»,
    «кожник», «невропатолог», «отоларинголог», «ухогорлонос», «сердечник»,
    «детский врач» ушли в train, поэтому hold-out теперь: «зубник»,
    «глазник», «дерматовенеролог», «нервный врач», «ушник»,
    «психоаналитик», «семейный/женский врач», «сердечный врач»,
    «детский доктор», «врач по почкам», «врач по щитовидке», «костоправ»,
    «специалист по операциям»;
  - hold-out выражения симптомов: «мигрень», «обсыпало», «зуб стреляет»...;
  - hold-out скелеты (`ood_a/b/c`);
  - композиционные hold-out пары специальность×симптом, которых нет в
    `PLAUSIBLE` (gp+toothache, psychologist+headache и т.д.).
- Проверено скриптом: hold-out слова и пары — 0 вхождений в train/val/iid,
  целостность парафраз-групп — 0 нарушений.

## Валидация

`validate.py` на каждом примере проверяет: помеченная специальность
упомянута, чужие специальности/симптомы не упомянуты (кроме
`extra_mentions` — конфликт «к терапевту или к дерматологу»), временная
фраза скопирована вербатим / при `TIME_UNKNOWN` временных фраз в тексте нет.
Тот же валидатор годится для фильтрации LLM-парафраз (контур B).

`self_check()` ловит пересечения «иголок» между метками тем же способом,
которым матчится валидация — по границам слов: «терапевт» не конфликтует
с «психотерапевтом» (приставка блокируется lookbehind), а вот «зубной»
внутри «зубная боль» — конфликт.

## Известные ограничения (v1)

- Точный дедуп — только по нормализованному тексту; почти-дубликаты
  (MinHash/эмбеддинги) не отфильтрованы.
- Ёмкость поверхности конечна: без расширения словаря train упирался в
  ~14k уникальных текстов; после итерации открытых источников (ниже)
  добирает 20k. Unsupported расширяется добавлением вариантов в
  `UNSUPPORTED_POOLS`.
- Отсутствуют: смешанный язык, упоминания конкретных врачей/клиник,
  много-интентные сообщения.

## Подключение внешних датасетов

Итоговый корпус — гибрид; у каждой записи есть поле `source`
(`synthetic` / `manual` / `hasd` / будущее `massive` / ...), чтобы мерить
качество по источникам отдельно.

### HASD — сделано (`synth/import_hasd.py`)

[andreaceto/hasd](https://huggingface.co/datasets/andreaceto/hasd) — 2 922
английские фразы для scheduling-чатбота (Apache-2.0, цитировать CLINC-OOS).
Перевод — детерминированный **NLLB-200-distilled-600M** (greedy на
DirectML), послепереводный глоссарий чинит кальки («назначение»→«запись»).
Запуск:

```bash
.venv-tr/Scripts/python synth/import_hasd.py
```

Пайплайн: фильтр сущностей (фразы с `practitioner_name`/`appointment_id`
дропаются, `appointment_type` — в ручную разметку) → перевод →
автосборка фрейма по иголкам + вербатимный временной спан → round-trip
валидация. Выход: `data/hasd_ru.jsonl` (booking, split=`ext_test`),
`data/hasd_unsupported_ru.jsonl` (негативы), `data/hasd_needs_review.jsonl`
(сомнительные, в обучение не идут), кэш переводов для перезапуска.

Нюансы, вскрытые при импорте:
- HASD — **академический** scheduling (советы с кураторами, защиты),
  не медицина: специальности/симптомы почти отсутствуют, поэтому метки
  в основном `UNKNOWN_SPECIALTY` — это честно по контракту. Ценность —
  независимые структуры фраз booking/reschedule/cancel и негативы.
- beam>1 на DirectML склеивает фразы батча — на DML всегда greedy;
  beam=4 доступен на CPU (теория: `.venv-tr` с transformers 4.46 поверх
  системного torch 2.4, чтобы не ломать torch-directml).

### MASSIVE ru-RU — сделано (`synth/import_massive.py`)

Источник: [amazon-massive-dataset-1.1](https://amazon-massive-nlu-dataset.s3.amazonaws.com/amazon-massive-dataset-1.1.tar.gz),
ru-RU = 16 521 профессионально переведённая фраза. Скрипт извлекает значения
слотов `date`/`time`/`date_time` (формат `[time : пять утра]`), ранжирует по
частоте и сохраняет:

- `data/massive_temporal_candidates.json` — 738 словесных временных фраз
  с частотами (курационный материал);
- `data/massive_calendar_reference.jsonl` — 2 948 полных calendar/datetime-фраз
  для будущего майнинга скелетов.

Курируемые добавления в `TEMPORALS` (блок «из MASSIVE» в `vocab.py`,
31 фраза): абсолютное время словами («в девять утра», «в два часа дня»,
«в полдень», «в пять тридцать вечера»), комбинации («завтра утром»,
«в пятницу вечером», «на выходных») и относительные («через месяц»).
Отброшено по правилам: прошедшее время, длительности («полчаса»),
голые числа, месяцы/числа (до v2 хардкод-парсера).

Архитектурное решение: модель копирует сырую фразу в слот `<TIME>`, а
канонические токены для бэкенда (`<TIME_10:00>`, `<DATE_TOMORROW>`)
вычисляет хардкод-парсер — тот же словарь, но с юнит-тестами вместо
обучения нормализации нейросетью. Корпус совместим с обеими схемами:
если позже захочется токены на выходе модели, парсер переразметит
`<TIME>`-спаны автоматически.

### CLINC150 — сделано (`synth/import_clinc.py`)

[DeepPavlov/clinc150](https://huggingface.co/datasets/DeepPavlov/clinc150):
стратифицированная подвыборка (12 фраз × 150 интентов), перевод тем же
детерминированным NLLB-конвейером (кэш `data/clinc_translations.json`),
round-trip фильтрация. Для клинического домена любая фраза CLINC —
не запись к врачу (рестораны, погода, будильники, банковские запросы),
поэтому всё — негативы `<UNSUPPORTED>`: **1 200 в train-аугментацию**
(`data/clinc_ru.jsonl`, split=`train_aug`, подмешивать к train.jsonl при
обучении) и **578 в ext_test**. Доля выбрана умеренно, чтобы негативы
не задавили booking (рекомендация обзора). Спорные переводы (5 шт.,
всплывали слова симптомов/специальностей) — в `data/clinc_needs_review.jsonl`.

### Скелеты из MASSIVE — сделано

Из `data/massive_calendar_reference.jsonl` (2 948 живых calendar-фраз)
намайнено 6 скелетов в `realize.py`: `mark_calendar` («пометь в моём
календаре приём к X»), `add_calendar`, `dont_forget` («не забудь записать
меня к X»), `check_spot` («проверь, есть ли место у X»), `move_simple`
(«перенеси мой приём к X»), `remove_cancel` («удали/сотри мою запись к X»).
Запросы расписания («что у меня запланировано») сознательно не взяты:
в контракте нет intent=query, корректная разметка была бы невозможна.

### Расширение поверхностей из открытых источников — сделано (`synth/expand_mining.py`)

Итерация закрытия дыры «незнакомая формулировка → UNSUPPORTED» (выявила
батарейка `train/test_new_intents.py`): словарь поверхностей новых интентов
был беден (7–12 формулировок на класс). Майнинг + перевод-адаптация:

- **CLINC150** (EN): calendar/confirm_reservation → check_booking,
  cancel/cancel_reservation → cancel, order_status/application_status →
  lab_status, bill_\*/pay_bill → paid, report_fraud/report_lost_card →
  complaint, international_visa → docs, vaccines → medical, yes/no/maybe →
  поверхности ответов;
- **MASSIVE ru-RU** (готовый русский): calendar_query/remove,
  takeaway_query, datetime_query (новый unsupported-пул «время-дата»);
- **SGD** (EN): цены; часы работы и лист ожидания в USER-репликах
  отсутствуют — тупик;
- **MedQuAD** (EN): вопросы о лечении → medical.

Перевод-адаптация — **локальная LLM** (llama.cpp/Vulkan из `.llm-local/`,
qwen2.5-1.5b-instruct; оба 8B-кванта ломают грамматику). Слабое место
1.5B — трансплантация домена («виза» не едет в «документы») — лечится
подсказкой целевого интента в промпте. Для интентов, которых в открытых
датасетах нет (schedule/waitlist/home_visit), — LLM-парафразы поверх
словаря и фраз батареи провалов. Всё проходит фильтры валидатора
(иголки/цифры/латиница/утечки доменов) и ручную ревизию; кэш переводов —
`data/expand_llm_cache.json`, кандидаты — `data/expand_surfaces.json`.

Итог: **+101 поверхность REQUESTS** (словарь ×1.5–2 по каждому интенту),
**+31 ответ да/нет**, пул `datetime`. Попутно исправлено: CLINC-негативы
больше не содержат интенты, ставшие позитивными классами (было:
«yes»/«cancel» размечены UNSUPPORTED — прямой конфликт меток).

### Модель и её текущее состояние

- **train/ — ОСНОВНАЯ модель** (решение зафиксировано после итерации
  открытых источников): decoder-only 6.84M (256/8/8), loss по target,
  генерация автоматом `constrained.py` (интенты и тривиальные да/нет —
  из `synth/vocab.py`, токенизатор `models/tokenizer_v2.json`;
  `models/tokenizer.json` остаётся общим с теггером — его веса привязаны
  к старым id). Метрики после расширения датасета: **val exact 0.992
  (intent 0.998), iid 0.992, OOD raw exact 0.090 / intent 0.945**
  (до расширения: 0.963 / 0.925 / 0.045). Батарейка новых интентов
  (`train/test_new_intents.py`): словарные поверхности 1.00, парафразы
  да/нет 5/6 (было 0/6), свежие парафразы живой речи ~0.5 — главный
  остаточный риск: незнакомая формулировка уходит в `<UNSUPPORTED>`.
  Теггер (`tagger/`) — экспериментальная BIO-архитектура, НЕ основная.

#### Доработка NLU по ТЗ (Этапы A+B+C) + итерация негативов — словарь расширен, ожидает переобучения

Корпус пересобран под ТЗ «доработка NLU-модели» и расширен по РГ-ТЕЛ-01
(скрипт.docx): пул `emergency` (§7.4, красные флаги без иголок), +39
поверхностей интентов (§6.x), поверхности «для прикрепления» (С-13),
цель сборки — 30 000. В пайплайн обучения вшиты внешние негативы:
1 200 CLINC (train_aug, как раньше) + 299 HASD train_aug —
`hasd_unsupported_ru.jsonl` расколот 299/299 на train_aug/ext_test
(`evaluate_all` фильтрует hasd_unsup по сплиту), тексты негативов вошли
в корпус BPE. Промежуточная итерация (20k + негативы) дала: val exact
0.989 (intent 1.000), негативы hasd_unsup 0.973 / clinc 0.997, приёмка
40/40; артефакты `models/model.pt`/`model.onnx`/`tokenizer_v2.json` —
предыдущей итерации и согласованы между собой; после расширения
словаря модель ждёт пересборки по runbook ниже. Попутно закрыты
композиционные дыры корпуса: «давит в груди × родственник» в
home_relative; train.py получил точное восстановление tied-веса через
forward (обход бага снятия весов с DirectML на длинных прогонах).

- **Этап A**: специальности `<CARDIOLOGIST>`, `<UROLOGIST>`,
  `<PEDIATRICIAN>`, `<ENDOCRINOLOGIST>`, `<ORTHOPEDIST>` (травматолог
  при этом переехал от хирурга к ортопеду); симптомы
  `<SYMPTOM_CHEST_PAIN>`, `<SYMPTOM_SHORTNESS_OF_BREATH>`,
  `<SYMPTOM_LOSS_OF_CONSCIOUSNESS>`, `<SYMPTOM_NAUSEA>`,
  `<SYMPTOM_VOMITING>`, `<SYMPTOM_JOINT_PAIN>` (суставные жалобы-шум
  «колено ноет» стали размеченным симптомом); разговорные синонимы
  «окулист/глазной», «дантист», «кожник», «невропатолог»,
  «отоларинголог/ухогорлонос», «сердечник», «детский врач» — в train,
  каждой специальности выдан новый hold-out синоним.
- **Этап B**: «талон» → BOOK («мой талон на когда» остался
  check_booking), «перезапишите» → RESCHEDULE, «направление к врачу» →
  BOOK+специальность (скелет referral), «ребёнок заболел»/«вызовите
  педиатра на дом» → HOME_VISIT (скелеты home_*, включая симптом у
  родственника), «работаете в субботу»/«в каком кабинете принимает
  врач» → SCHEDULE (скелеты sched_day/sched_cabinet), «врач
  нагрубил/нахамил» → COMPLAINT, «сколько стоит приём у кардиолога» →
  PAID со специальностью в слоте (скелет paid_spec).
- **Этап C**: «не могу прийти» — поверхности RESCHEDULE (не
  бессонница); «у мужа давит в груди» — фрейм HOME_VISIT с
  `<SYMPTOM_CHEST_PAIN>` (голое «да» исключено конструктивно).
- **Приёмка**: `train/test_nlu_acceptance.py` — 40 регламентных реплик
  С-01…С-15 (до переобучения пропуск с инструкцией). С-14 (экстренные)
  остаётся на safety-слое осознанно; Этап D (абсолютные даты) — regex,
  отложен по ТЗ.
- `manual_gold.jsonl` пополнен десятью затравками новых поверхностей
  (талон/направление/перезапишите/суббота/кабинет/нагрубил/грудь/...).

#### Runbook пересборки основной модели (на машине обучения)

```bash
python synth/build_dataset.py            # корпус, только stdlib
# внешние импорты (если data/*.jsonl нет на машине): import_hasd /
# import_clinc (.venv-tr, NLLB), expand_mining (.llm-local) — кэшируемые
python train/tokenizer_train.py          # models/tokenizer_v2.json (Этап A.4)
python train/train.py --tokenizer models/tokenizer_v2.json \
    --d-model 256 --n-layers 8 --n-heads 8 --save models/model.pt
python train/evaluate_all.py model.pt tokenizer_v2.json
python train/export_onnx.py              # models/model.onnx
pytest train/test_nlu_acceptance.py -q   # приёмка: 40/40 (ТЗ, п. 9.3)
python train/test_new_intents.py         # регресс старых интентов
```

Коммитить `model.pt`/`tokenizer_v2.json`/`model.onnx` только тройкой —
веса и токенизатор обязаны переучиваться вместе.
- **train/oov_input.py — e5-резолвер входа**: незнакомое слово реплики
  заменяется ближайшей TRAIN-поверхностью словаря (multilingual-e5-small,
  порог 0.80, одна подмена на реплику; служебные слова неприкосновенны).
  Помогает на OOD-синонимах специальностей («дантист»→«стоматолог»), но
  на новой модели портит обычные фразы («меня записывали»→«меня
  высыпало»). В коде (`telephone.FrameModelNlu`) включён по умолчанию —
  в проде выключать явно: `TEL_FMODEL_RESOLVER=0` (нужен `.venv-tr`:
  там рабочая связка torch 2.4 + transformers 4.46).
- **train/DEPLOY.md — гайд по прод-развёртыванию** для backend-
  разработчика: контракт, совместимость артефактов, FastAPI-сервис,
  разбор фрейма, ONNX-путь, обновление модели, мониторинг.
- **telephone/**: менеджер диалога телефонии на полном каталоге —
  батарейка из 19 сценариев (см. `telephone/README.md`).

#### Мультилейбл-модель: ONNX для Java-бэкенда (`multilabel_model.onnx`)

Параллельный кандидат frame-модели: TF-IDF word(1,2) + OneVsRest
LogReg, 50 тегов, декодирование по группам грамматики фрейма. Один
линейный прогон, без цикла генерации; переобучение — ~80 секунд на
CPU. Полный контракт и алгоритмы — **`models/MULTILABEL_INTEGRATION.md`**
(обязателен к прочтению перед интеграцией).

Файлы поставки (все в `models/`):

| Файл | Назначение |
| :-- | :-- |
| `multilabel_model.onnx` | граф `float32[1, 19839] → вероятности[50]`; парность со sklearn 9.7e-08 |
| `multilabel_features.json` | словарь признаков (19 839) + idf + порог тегов |
| `multilabel_tags.json` | порядок 50 выходов: группа (intent/spec/sym/clar) + тег |
| `oov_dict.json` | замены незнакомых слов (185) — применять ДО векторизации |
| `multilabel_testvectors.json` | 10 фраз → ожидаемые теги (юнит-тест Java) |

Пайплайн Java: `text → oov_dict → векторизация → ONNX → декодирование`.
Векторизация (детали в MULTILABEL_INTEGRATION.md §2.1): lowercase,
токены `\w\w+`, уни- и биграммы через пробел, `tf = 1+ln(count)`,
`× idf`, L2-норма. Декодирование: intent — argmax; для
`<YES>/<NO>/<UNSUPPORTED>` фрейм голый; spec — argmax (включая
`<UNKNOWN_SPECIALTY>`); симптомы/`<NEEDS_CLARIFICATION>` — порог 0.5.
Временной слот — хардкод-таблица `TEMPORAL_ENTRIES` (та же, что у
frame-модели): самый длинный вход по границам слов, не найдено →
`<T_UNKNOWN>`.

Метрики экспортной ветки (полная таблица пяти веток —
`models/multilabel_report.txt`): val intent 0.932 / exact 0.811,
iid 0.937 / 0.827, **ood intent 1.000** (у frame-модели 0.975),
негативы hasd_unsup 0.930 / clinc 0.978. Слабое место — ood-синонимы
специальностей (0.150): лексическая природа признаков. Лучшие
показатели у ветки с лемматизацией + char-граммами (val exact 0.861,
приёмка 39/40) — только Python-инференс: skl2onnx не конвертирует
char_wb-анализатор и не повторяет sklearn-токенизацию кириллицы внутри
графа, поэтому в ONNX уезжает word-ветка, а векторизация — на клиент.

Переобучение: `python synth/build_dataset.py --train 30000` →
`python train/train_multilabel.py` →
`python train/export_multilabel_onnx.py` (проверяет парность сам).
Генеративная `model.onnx` (предыдущая версия) остаётся в строю.

### Дальше по плану

- Живая речь: каждый цикл LLM-парафразирования даёт ~+10 п.п. на свежих
  формулировках — пайплайн готов, перезапуск дешёв (кэш). Альтернативы:
  увеличение модели или перенос каталога в теггер (BIO-архитектура
  устойчивее к OOD-синонимам: 0.995 против 0.090 на старом датасете).
- Косвенные отмены («не приду, снимите запись», «приём не актуален») и
  отыменные формы («отмена визита») — вне покрытия, следующий кандидат
  на расширение.
- **Synthetic Outpatient Scheduling Dataset** — не NLU-корпус; годится
  для mock-backend (слоты, расписание, no-show).
- HASD остаётся слабым: независимые формулировки scheduling-речи.

Ручной `manual_gold.jsonl` (25 фраз-затравок, включая «зуб разрывает, чё
есть вечером после смены?») — единственный прокси реальной речи; его стоит
пополнять фразами людей, не видевших генератор.
